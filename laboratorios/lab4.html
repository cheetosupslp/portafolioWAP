01

Objetivo de la Práctica

Demostrar la identificación y explotación de una vulnerabilidad de File Path Traversal en la que la aplicación elimina las secuencias de recorrido y posteriormente realiza un URL-decode adicional. El objetivo es recuperar el contenido del archivo /etc/passwd mediante el uso de doble codificación URL.

02

Marco Teórico

File Path Traversal es una vulnerabilidad que permite a un atacante acceder a archivos fuera del directorio permitido mediante la manipulación de parámetros que construyen rutas de archivos.

Esta vulnerabilidad afecta principalmente el principio de Confidencialidad del modelo CIA y se encuentra catalogada dentro de A01:2021 – Broken Access Control del OWASP Top 10.

En este laboratorio la aplicación elimina las secuencias ../ y después realiza un URL-decode extra del valor recibido. Esta doble operación permite evadir el filtro mediante doble codificación URL (%252f en lugar de /).

03

Desarrollo

1. Acceso al laboratorio

Se accedió al laboratorio oficial de PortSwigger: 

https://portswigger.net/web-security/file-path-traversal/lab-superfluous-url-decode

Al hacer clic en Access the lab se carga una aplicación de tienda en línea vulnerable.

2. Configuración de Burp Suite

Se utilizó Burp Suite Community Edition. Se abrió el navegador integrado desde la pestaña Proxy → Intercept → Open Browser para que todo el tráfico pasara a través del proxy.

3. Identificación del parámetro vulnerable

Al navegar por los productos se observó que las imágenes se cargan mediante peticiones del tipo: 

GET /image?filename=XX.jpg HTTP/1.1

El parámetro filename es controlado por el usuario y se utiliza para construir la ruta del archivo en el servidor.

4. Prueba de payloads anteriores

Se probaron los payloads de los laboratorios anteriores: 

../../../etc/passwd
/etc/passwd
....//....//....//etc/passwd

Todos fallaron, confirmando que la aplicación elimina las secuencias de recorrido y aplica un procesamiento adicional.

5. Explotación con doble codificación URL

Se modificó el parámetro filename por el siguiente payload: 

..%252f..%252f..%252fetc/passwd

La petición final quedó de la siguiente forma:

GET /image?filename=..%252f..%252f..%252fetc/passwd HTTP/1.1

Al enviar la petición, el servidor devolvió el contenido completo del archivo /etc/passwd, resolviendo el laboratorio.

04

Explicación Técnica del Payload

El payload utilizado fue: 

..%252f..%252f..%252fetc/passwd

¿Por qué funciona?

La aplicación realiza dos operaciones en este orden:

  1. Elimina las secuencias de path traversal (../).
  2. Después realiza un URL-decode adicional del valor.

Un ../ normal es detectado y eliminado. Sin embargo, al usar doble codificación URL:

  • / se codifica como %2f
  • %2f se vuelve a codificar como %252f (el símbolo % se convierte en %25)

Cuando se envía ..%252f:

  1. El filtro no detecta la secuencia ../ (está codificada), por lo tanto no la elimina.
  2. Luego el servidor hace el URL-decode extra y convierte %252f → %2f → /.
  3. Finalmente el valor se transforma en ../../../etc/passwd, que sí funciona.
05

Conclusiones

En este laboratorio se demostró que eliminar las secuencias ../ y realizar un URL-decode posterior no es una defensa suficiente. Mediante el uso de doble codificación URL (%252f) fue posible evadir el filtro y acceder al archivo /etc/passwd.

Esta práctica refuerza la importancia de implementar validaciones robustas que contemplen múltiples capas de codificación y que se realicen sobre el valor final después de todos los decodificados, además de preferir listas blancas y canonicalización de rutas.

El uso de Burp Suite (Proxy + Repeater) facilitó la prueba controlada de diferentes niveles de codificación hasta encontrar el payload efectivo.
