01

Objetivo de la Práctica

Demostrar la identificación y explotación de una vulnerabilidad de File Path Traversal en la que la aplicación valida que la ruta suministrada comience con una carpeta específica (/var/www/images). El objetivo es recuperar el contenido del archivo /etc/passwd respetando dicha validación y luego saliendo del directorio permitido.

02

Marco Teórico

File Path Traversal es una vulnerabilidad que permite a un atacante acceder a archivos fuera del directorio permitido mediante la manipulación de parámetros que construyen rutas de archivos.

Esta vulnerabilidad afecta principalmente el principio de Confidencialidad del modelo CIA y se encuentra catalogada dentro de A01:2021 – Broken Access Control del OWASP Top 10.

En este laboratorio la aplicación transmite la ruta completa del archivo y valida que el valor del parámetro empiece con la carpeta esperada (/var/www/images). Esta protección puede ser evadida manteniendo el prefijo requerido y añadiendo secuencias de recorrido (../) después de él.

03

Desarrollo

1. Acceso al laboratorio

Se accedió al laboratorio oficial de PortSwigger: 

https://portswigger.net/web-security/file-path-traversal/lab-validate-start-of-path

Al hacer clic en Access the lab se carga una aplicación de tienda en línea vulnerable.

2. Configuración de Burp Suite

Se utilizó Burp Suite Community Edition. Se abrió el navegador integrado desde la pestaña Proxy → Intercept → Open Browser para que todo el tráfico pasara a través del proxy.

3. Identificación del parámetro vulnerable

Al navegar por los productos se observó que las imágenes se cargan mediante peticiones que incluyen la ruta completa: 

GET /image?filename=/var/www/images/XX.jpg HTTP/1.1

El parámetro filename es controlado por el usuario y se utiliza para construir la ruta del archivo en el servidor. La aplicación valida que el valor comience con /var/www/images.

4. Prueba de payloads anteriores

Se probaron los payloads de los laboratorios anteriores: 

../../../etc/passwd
/etc/passwd
....//....//....//etc/passwd
..%252f..%252f..%252fetc/passwd

Todos fallaron porque no cumplían con la validación de inicio de ruta.

5. Explotación respetando la validación

Se modificó el parámetro filename por el siguiente payload: 

/var/www/images/../../../etc/passwd

La petición final quedó de la siguiente forma:

GET /image?filename=/var/www/images/../../../etc/passwd HTTP/1.1

Al enviar la petición, el servidor devolvió el contenido completo del archivo /etc/passwd, resolviendo el laboratorio.

04

Explicación Técnica del Payload

El payload utilizado fue: 

/var/www/images/../../../etc/passwd

¿Por qué funciona?

La aplicación valida que el valor del parámetro filename comience con la cadena: 

/var/www/images

Si el valor no empieza con esa ruta, la petición es rechazada.

Al enviar /var/www/images/../../../etc/passwd:

  1. La validación se cumple (sí comienza con /var/www/images).
  2. Después el servidor procesa las secuencias ../:
  • Primer ../ → sale de /images/
  • Segundo ../ → sale de /www/
  • Tercer ../ → sale de /var/ y llega a la raíz del sistema

Finalmente se lee el archivo /etc/passwd.

05

Conclusiones

En este laboratorio se demostró que validar únicamente que una ruta comience con una carpeta específica no es una defensa suficiente. Al respetar el prefijo requerido (/var/www/images) y añadir secuencias de recorrido fue posible acceder al archivo /etc/passwd.

Esta práctica refuerza la importancia de implementar validaciones más robustas, como la canonicalización de rutas (resolver la ruta real antes de usarla) y el uso de listas blancas de archivos permitidos.

El uso de Burp Suite (Proxy + Repeater) permitió identificar rápidamente el formato de la ruta completa y probar el payload de forma controlada.
