VULN-13

"Evasión de controles del lado del cliente y alteración de lógica de facturación"

← Volver al proyecto PR02

Descripción técnica y causa raíz

Se descubrió una vulnerabilidad crítica en la lógica de negocio del módulo de pagos (pago.php). El sistema permite a un usuario alterar el monto de cobro antes de enviarlo al procesador final, eludiendo las restricciones de interfaz que simulaban proteger la tarifa original.

Causa raíz: Violación del principio fundamental de seguridad "Nunca confíes en el cliente" (Zero Trust). El backend depende de controles superficiales en el HTML (el atributo readonly o campos ocultos) para mantener la integridad del precio. Al recibir el formulario (POST), el servidor no recalcula ni valida criptográficamente el monto contra la base de datos interna, aceptando ciegamente la cantidad manipulada.

Comprobación de los hallazgos

  1. Se inició un proceso de pago legítimo dentro de la plataforma, llegando al formulario de confirmación en pago.php.
  2. Se identificó el campo de texto que mostraba el total a pagar, el cual estaba bloqueado visualmente por el atributo HTML readonly.
  3. Utilizando las herramientas de desarrollador del navegador (Inspect Element), se eliminó el atributo readonly del código fuente local.
  4. Se modificó el valor numérico original por una cantidad inferior (ej. de $1,500.00 a $1.00).
  5. Al enviar el formulario modificado, el backend procesó el pago de manera exitosa tomando como válido el monto alterado.

Impacto y riesgo

Nivel Crítico. Representa un vector directo para el fraude financiero sistémico. Cualquier ciudadano con conocimientos básicos de navegación web puede evadir el costo real de los servicios, multas o impuestos, traduciéndose en pérdidas económicas directas y masivas para la institución (evaluado formalmente en las matrices de riesgo R-21 a R-23).

Mitigaciones

  • El monto a pagar jamás debe ser enviado o leído desde el cliente hacia el servidor durante el procesamiento del pago.
  • El backend debe recalcular de forma independiente la tarifa final consultando el ID del servicio o producto directamente en la base de datos de precios interna.
  • Si los flujos de terceros requieren enviar montos en el frontend temporalmente, se deben asegurar utilizando firmas criptográficas (HMAC) vinculadas a la sesión del usuario.
