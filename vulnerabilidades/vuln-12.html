VULN-12

"Referencia Directa Insegura a Objetos (IDOR / BOLA) en módulo de facturación"

← Volver al proyecto PR02

Descripción técnica y causa raíz

El portal permite a los ciudadanos consultar sus recibos y estados de cuenta a través de un identificador numérico secuencial en la URL o API. Sin embargo, se detectó que es posible acceder a los documentos financieros de cualquier otro ciudadano simplemente modificando dicho identificador.

Causa raíz: Ausencia de autorización a nivel de objeto (Broken Object Level Authorization - BOLA). El backend valida que el usuario tenga una sesión activa, pero falla de manera crítica al no verificar si el registro específico solicitado en la base de datos pertenece legítimamente al propietario de dicha sesión.

Comprobación de los hallazgos

  1. Se inició sesión legítimamente con una cuenta de ciudadano estándar.
  2. Se accedió a la visualización de una factura propia, observando que la URL dependía de un parámetro directo (ej. ver_factura.php?id=1045).
  3. Se modificó el parámetro numérico de forma incremental u horizontal (ej. id=1046 o id=1047).
  4. El servidor omitió la validación de propiedad y devolvió el recibo, datos personales y montos de cobro de un tercer usuario sin autorización.

Impacto y riesgo

Nivel Alto. Esta vulnerabilidad representa una violación directa a la privacidad y confidencialidad de la Información de Identificación Personal (PII) e información financiera. Un atacante puede crear un script automatizado para descargar y enumerar masivamente todos los recibos de los ciudadanos iterando sobre los identificadores (Data Scraping).

Mitigaciones

  • Implementar controles estrictos de autorización a nivel de objeto en el backend: cada consulta SQL para visualizar o modificar registros debe incluir una validación contra el ID del usuario autenticado (ej. SELECT * FROM facturas WHERE id_factura = ? AND id_usuario_sesion = ?).
  • Sustituir los identificadores enteros autoincrementales (como 1045) por identificadores únicos universales e impredecibles (UUIDv4) para evitar la enumeración de registros.
  • Asegurar mediante pruebas de caja blanca que el modelo de control de acceso se aplique de manera transversal en todos los endpoints de consulta y modificación.
