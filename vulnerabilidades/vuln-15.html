VULN-15

"Fuga de Información Sensible en Encabezados HTTP (API de Infraestructura)"

← Volver al proyecto PR02

Descripción técnica y causa raíz

El endpoint que consulta el estado de los servicios de TI (/api/infrastructure-status.php) expone un token de validación interno de forma encubierta a través de una cabecera de respuesta HTTP personalizada (x-interafas-validation).

Causa raíz: Al igual que en el Reto 11, el equipo de desarrollo o infraestructura dejó código de depuración (debug) o de pruebas activo en el ambiente de producción, provocando que el servidor inyecte metadatos sensibles directamente en el tráfico HTTP saliente. Existe una falla en la validación y limpieza de despliegues (Release Management) y ausencia de controles de saneamiento de salida (Output Sanitization) a nivel de servidor web o proxy reverso.

Comprobación de los hallazgos

  1. Se ingresó al portal de INTERAFAS y se navegó hacia la sección de "Infraestructura".
  2. Se abrieron las herramientas de desarrollo del navegador (F12) posicionándose en la pestaña Network (Red).
  3. Se recargó la página (F5) para capturar todo el tráfico y las peticiones asíncronas generadas por el portal en segundo plano.
  4. Se localizó la petición GET realizada dinámicamente al endpoint: http://localhost:8080/api/infrastructure-status.php.
  5. Se seleccionó dicha petición y se navegó a la sección de Headers, específicamente dentro del bloque de Response Headers.
  6. Se identificó la cabecera no estándar inyectada por el servidor, capturando la bandera correspondiente.

Impacto y riesgo

Confidencialidad: Aunque el impacto directo a datos de usuario es nulo en este endpoint, la filtración constante de metadatos de desarrollo facilita la fase de reconocimiento para un atacante. Le confirma que la arquitectura permite cabeceras personalizadas y evidencia una falta de madurez en los controles de paso a producción.

Riesgo Organizacional: Representa una falla en los procedimientos operativos estandarizados. Hoy es una bandera de laboratorio, pero mañana esta misma práctica podría exponer un token de autorización real de una API interna.

Cadena de ataque

Este hallazgo se clasifica dentro de la recolección de inteligencia (Information Gathering). Al inspeccionar las peticiones automáticas de la interfaz de usuario, un atacante identifica endpoints de la API que operan en segundo plano. Estos endpoints son candidatos ideales para probar ataques de enumeración (Fuzzing) o Inyección (SQLi) debido a que suelen tener menos medidas defensivas que los formularios visibles.

Mitigaciones

  • Limpieza de Código (Code Review): Auditar el código fuente del archivo infrastructure-status.php y eliminar las funciones (como header() en PHP) que inyecten estas variables de validación en los ambientes de producción.
  • Hardening del Servidor / Proxy: Configurar el servidor web Apache, Nginx o el Web Application Firewall (WAF) para que intercepte las respuestas del backend y elimine sistemáticamente cualquier cabecera que no pertenezca a una lista blanca estricta (permitiendo solo cabeceras estándar de seguridad y contenido).
