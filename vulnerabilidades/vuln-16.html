VULN-16

"Evasión de Control de Acceso por IP Spoofing en Gateway Operacional"

← Volver al proyecto PR02

Descripción técnica y causa raíz

El gateway operacional (/operations/gateway.php) restringe el acceso al sistema basándose en la dirección IP de origen, declarando una política que bloquea las peticiones externas y permite exclusivamente el tráfico del segmento interno (10.40.20.0/24). Sin embargo, es posible evadir esta restricción falsificando la IP de origen.

Causa raíz: El servidor confía ciegamente en encabezados HTTP controlables por el cliente (específicamente X-Forwarded-For) para determinar la dirección IP del usuario, en lugar de utilizar la dirección IP real del socket de la conexión TCP a nivel de red. Esta es una falla crítica de validación de identidad en arquitecturas que no sanitizan los encabezados de proxy.

Comprobación de los hallazgos

  1. Se intentó acceder directamente al gateway, recibiendo un código HTTP 403 Forbidden y un mensaje que declaraba la política de restricción de red.
  2. Se identificó el segmento operacional objetivo (OPS-NET-20 / 10.40.20.0/24) obtenido en fases de reconocimiento previas.
  3. Se desarrolló un script en PowerShell utilizando Invoke-WebRequest para inyectar el encabezado de proxy X-Forwarded-For: 10.40.20.10.
  4. Al enviar la petición, el servidor omitió el bloqueo 403 y aceptó la solicitud como si proviniera legítimamente de la zona operacional interna.
  5. La prueba de concepto fue exitosa, revelando el token de validación en el encabezado de respuesta X-INTERAFAS-Validation (sin acceder aún a variables de proceso).

Impacto y riesgo

Nivel Alto. Esta vulnerabilidad destruye la segmentación de red perimetral a nivel de aplicación (Capa 7). Permite que un atacante completamente externo "cruce la frontera" y simule estar físicamente dentro de la red OT/SCADA de la institución, obteniendo la puerta de entrada para interactuar con sistemas de control y variables de proceso sin requerir credenciales.

Mitigaciones

  • Extraer la IP del cliente exclusivamente desde la capa de transporte (ej. $_SERVER['REMOTE_ADDR']) a menos que la petición provenga de un proxy reverso o balanceador de carga institucional debidamente configurado.
  • Si la infraestructura requiere el uso de X-Forwarded-For, el backend debe validar primero que la IP que envía dicho encabezado pertenezca a una lista blanca (Whitelist) estricta de proxies confiables.
  • Implementar una arquitectura Zero Trust: no confiar en las conexiones únicamente por su dirección IP o segmento de red; exigir autenticación mutua y validación de tokens de identidad en el gateway.
