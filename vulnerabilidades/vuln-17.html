VULN-17

"Control de Acceso Inconsistente y Exposición de Telemetría (Broken Access Control en API OT)"

← Volver al proyecto PR02

Descripción técnica y causa raíz

El servicio que suministra los datos en tiempo real de la planta (/operations/telemetry.php) expone las variables de proceso industrial sin requerir que el usuario esté autenticado en el Centro de Operaciones.

Causa raíz: Existe una asimetría en los controles de seguridad. Mientras que el panel principal de operaciones exige tanto estar en la red correcta como tener una sesión de usuario válida, el endpoint secundario que alimenta el panel (la API de telemetría) fue programado para confiar exclusivamente en la procedencia de la red (network-only), omitiendo la verificación del estado de la sesión (Operational-Session: missing). Esto representa una falla crítica en el Diseño de Autorización y ausencia de Defensa en Profundidad (Zero Trust). Los desarrolladores asumieron erróneamente que cualquier petición proveniente de la red operacional está inherentemente autorizada para consumir recursos.

Comprobación de los hallazgos

  1. Continuando con la falsificación de IP del Reto 16 (X-Forwarded-For: 10.40.20.10), se accedió al portal /operations/login.php.
  2. Se inspeccionó el código fuente HTML de la página e identificó el archivo JavaScript responsable de la lógica del HMI: <script src="/operations/assets/ops-client.php" defer></script>.
  3. Se solicitó dicho archivo mediante PowerShell (inyectando la cabecera de proxy) para analizar su contenido y descubrir la ruta del endpoint de datos: telemetryEndpoint: /operations/telemetry.php.
  4. Se realizó una petición GET directa hacia /operations/telemetry.php utilizando PowerShell sin enviar cookies ni credenciales, únicamente la cabecera de origen falsificado.
  5. El servidor devolvió un HTTP 200 OK, entregando los datos telemétricos de la planta.
  6. Al inspeccionar las cabeceras de respuesta, se confirmó la falla lógica mediante los valores Monitoring-Authorization: network-only y Operational-Session: missing, extrayendo la bandera del reto.

Impacto y riesgo

Confidencialidad Operativa (Nivel Crítico): Aunque el atacante no puede modificar valores (todavía), obtiene "ojos sobre la planta". Puede monitorizar en tiempo real las temperaturas, niveles, caudales y presiones del sistema hídrico.

Riesgo Operativo (Inteligencia para Sabotaje): Conocer el estado exacto de las variables de proceso es el requisito indispensable para planificar un ataque físico exitoso. Un atacante necesita saber cuándo un tanque está lleno o una válvula está bajo presión para que su comando de sabotaje cause el máximo daño físico (cavitación, derrames, explosiones).

Cadena de ataque (Kill Chain ICS/SCADA)

Este hallazgo enlaza perfectamente con la vulnerabilidad anterior. En la VULN-16 se logró "conectar el cable" a la red operacional mediante Spoofing. En esta VULN-17, se exploró pasivamente esa red, descubriendo y explotando una API mal configurada que brinda visibilidad total de la planta sin necesidad de robar contraseñas. El siguiente paso lógico en la cadena es pasar de la monitorización pasiva a la manipulación activa de los actuadores, válvulas o sistemas de mantenimiento.

Mitigaciones

  • Verificación de Sesión Obligatoria (Middleware): Implementar un componente centralizado que intercepte el 100% de las peticiones hacia el directorio /operations/ (incluyendo APIs y assets dinámicos) y valide criptográficamente la existencia de un token de sesión activo antes de procesar la solicitud.
  • Enfoque de Confianza Cero (Zero Trust): Abandonar el modelo de seguridad basado en el perímetro. La dirección IP (incluso si proviene de un segmento OT validado por un firewall) nunca debe ser el único factor para autorizar el acceso a datos industriales.
